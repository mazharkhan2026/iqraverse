## 3. Mandatory MDCAT content and full mock gate
The academic SRS and DEC register use PMDC 2025 curriculum applicable to 2026; verify the applicable official edition at implementation/publishing time and store provenance. The specified baseline is 180 questions, 180 minutes (10,800 seconds), +1 correct, 0 incorrect/unanswered, no negative marking; subject quotas below. Difficulty distribution: 15% easy, 70% medium (official moderate), 15% hard (official difficult), i.e. 27/126/27 across the paper.

| Subject | Questions per mock | Initial reviewed bank target |
|---|---:|---:|
| Biology | 81 | 100 |
| Chemistry | 45 | 100 |
| Physics | 36 | 100 |
| English | 9 | 100 |
| Logical Reasoning | 9 | 100 |
| Total | 180 | 500 |

The 500-item target comes from DEC-12, not an inventory already created. It is insufficient by itself to guarantee eligible quotas, difficulty balance or non-repeating full papers (two disjoint papers require at least 162 Biology items). Before release, seed reviewed licensed/original questions with topic, difficulty, key and explanation, test simultaneous subject and difficulty constraints, report gaps, and expand targeted pools. Proposed assembly: select approved unique question IDs using a constrained quota solver; prefer unseen questions and randomize among eligible choices; do not silently lower quotas, duplicate questions or imply every paper is entirely new. Return 409 INSUFFICIENT_QUESTION_BANK when no valid allocation exists. Keep configured retake limits server-side. Full 180-item attempt, grade fixtures and expiry/resume must pass; do not mark 30% complete with shortened mocks only.

For development, start with approximately 40 reviewed original MDCAT sample MCQs plus small NAT and IELTS reading sample banks; these are fixtures, not full mocks. Import only authorized past-paper material with individually stored, reviewed questions and original paper/edition references. Preserve the 500-item MDCAT target. Suggested starter targets: 15–20 reviewed questions each for NAT and IELTS reading, adjusted to support actual practice and a short timed test. Do not label an unverified pattern as official.

## 4. Student and teacher workflows
Student signs up once → chooses MDCAT, NAT or IELTS workspace → study or Build My Quiz (topic/subject/difficulty/count) or Exam Simulation (published blueprint; full MDCAT, labeled starter NAT/IELTS) → answer → submit/expire → review → targeted practice. No course enrollment required for independent preparation. Backend fixes attempt order, item versions and deadlines; saves answers; finalizes once; never sends keys before finalization.
Teacher applies with evidence → admin verifies → creates course/product draft → adds recorded content/notes and reviewed assessments → submits → admin approves/publishes revision → student discovers and enrolls for free → learns and completes lessons → teacher sees course-specific progress. Paid purchasing is a later sandbox workflow. Proposed course completion = completed required lessons / required lessons in enrolled published revision; zero required lessons = not applicable. Quiz accuracy tracked separately. Preserve course revision access and progress; define migration of old enrollments before course release. Admin can revoke access immediately without erasing historical attempts; instructor cannot self-approve or view private independent data.

## 5. Assessment and analytics
30% score: sum approved correct-answer marks; MDCAT full mock max 180; other assessments use their own blueprint maximum. IELTS starter reading scores are raw objective marks only, not bands. Practice accuracy = correct answered / answered, with denominator visible; no answered items = unassessed. For weak topics, retain v2 proposed rule: below 60% on at least 3 distinct answered logical questions within the same user/exam variant/syllabus/topic and mode scope; latest eligible graded answer per logical question (prevents edited versions/retries inflating evidence). Exactly 60% not weak; fewer than 3 = insufficient. Unanswered counts zero in mock grade but not in mastery accuracy. Separate practice/mock/course filters; default independent analytics must not include course results. No cross-exam aggregate. Recommendations link to eligible reviewed content; explain trigger. Weighted formula at 60% needs explicit review and golden tests.

Future NestJS → authenticated FastAPI AI service → Ollama, ChromaDB and local embeddings; no public model/vector ports. PostgreSQL authoritative for permissions. Docker local DB, GitHub, Postman, Swagger/OpenAPI; pin stable compatible tool versions in lockfiles. Prisma migrations proposed, one migration authority under backend/prisma. No Supabase dependency or different framework assumed. Storage/email/hosting providers and exact versions pending.
Security defaults retained from v2: Argon2id, short access JWT, hashed rotating refresh sessions, web refresh HttpOnly Secure SameSite cookie via same-site proxy, mobile refresh secure storage; web refresh token absent from JSON. CSRF protection for cookie actions, explicit CORS, validation, rate limits, single-use hashed expiring verification/reset tokens, audit events, role AND ownership checks, server-side admin bootstrap. No secrets in clients or Git. Define and review browser/mobile transport contract before auth integration; no actual credentials in docs. Secure file type/size/signature checks and private signed URLs.

## 7. Unified logical database baseline (not executable migrations)
UUID PKs, UTC timestamps, snake_case DB, camelCase JSON; FK/unique constraints and indexes on scope/status/ownership. Names below are proposed canonical names; review against actual branch schemas before migration. Do not create duplicate old/new tables for the same entity.
- Identity: users, profiles, roles, user_roles (grant/revoke metadata), role_permissions, auth_identities (later providers), refresh_sessions, verification_tokens, reset_tokens, instructor_verifications (evidence/review). No tutor tables or role.
- Curriculum: exams → exam_variants → syllabus_versions (edition, applicability_year, source_uri, status) → subjects → chapters → topics → curriculum_lessons. One published edition per variant for new attempts; historical references preserved. Variant and syllabus filters must agree.
- Content: sources (rights/provenance/reviewer), assets (owner, private storage key, hash, MIME, size), resources, resource_versions (immutable content and independent review/index status), passages. Link approved curriculum lessons to resources; keep instructor ownership and scope. Preserve optional past-paper identity/year/edition and question order through source metadata or a paper-to-question mapping; do not store an entire paper as one scored item.
- Questions: questions (logical ID, topic, owner, platform/course scope), question_versions (format, difficulty, prompt, passage, options_json, answer_key_json, explanation, source_version, status, marks), moderation_reviews. For MDCAT enforce exactly one valid correct option among four options as the proposed default, approved immutable version, source and explanation. Initial NAT and IELTS reading objective items use the same single_select format, with optional reading passage and exactly one approved key. Future mixed formats use validated per-format JSON; not active now. One current approved version per logical question, snapshot old versions.
- Assessments: blueprints (variant, syllabus, version, duration, scoring policy, retake limit, full-length flag, status), blueprint_sections (subject quotas, allowed formats), difficulty quotas at paper level; assessments (practice/mock/course), assessment_items; attempts (user, assessment, variant, syllabus, mode, status, start/deadline/submission, marks), attempt_items (question version, order, presentation snapshot, marks), attempt_answers (one per item, answer, grading, timestamp), idempotency_records. Unique item order/logical question per attempt; locks/transactions for save/finalize, immutable keys, expiry job + lazy checks.
- Courses: categories, courses (instructor, variant, category, product_type, state), course_revisions, course_lessons, course_revision_lessons (published membership), course_assessments, enrollments (user/course, revision, access state), lesson_progress (enrollment + revision lesson, completed_at). Keep curriculum and course lesson namespaces distinct; support notes/test packages without duplicating exam catalog. Access and progress tied to approved revision; no live payment fields required for 30%.
- Analytics: compute from eligible finalized answers with indexes; no duplicate counters initially. Later versioned topic_metrics/recommendation rules if necessary. audit_events record privileged actions. Later: private_documents, rag_chunks_manifest, ai_runs, ai_citations, separate provisional AI practice storage, marketplace_listings, mock_transactions, notifications. RAG permission checks before and after retrieval; shared/private isolation and revoke-before-purge. No tutoring schema.
